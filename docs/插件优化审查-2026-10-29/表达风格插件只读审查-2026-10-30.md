# 表达风格插件 v0.1.0 只读审查

审查依据：当前磁盘上的 BOT项目交接手册.md §17.4、§17.10–17.13、§17.18，以及对应 8 个文件。仅评审接口一致性、10 项未验证点及非目标；没有增加功能需求。未修改插件、未安装或重载、未调用付费模型。

结论：**当前版本不宜启用注入或定时学习。12 项原有测试全部复跑通过，但没有覆盖下面已复现的阻断问题。**

## 一、接口与实现问题（按影响排序）

### 1. P1：approved 查询导致所有风格注入失败

位置：`plugins/astrbot_plugin_dafeiyu_style/store.py:182`、`main.py:249`。

approved 对三张表统一 `ORDER BY used_count`，但 jargon 和 few_shots 没有这个列。新建空库调用 approved('jargon', 'g1') 和 approved('few_shots', 'g1') 均报 `no such column: used_count`；无需存在黑话或示例记录即可复现。

inject_style 总会依次查询三张表，异常被外层捕获后返回，已经通过的普通规则也无法注入；导出同样受影响。

最小修改：按表使用存在的排序列；若不需要使用计数，不要为了统一排序增加字段。补三张表分别查询及完整 hook 注入的测试。

### 2. P1：群过滤在 LIMIT 后执行，会永久饿死后面的群

位置：`learning.py:28–41`。

read_events 先取所有群最早的 100 条合格消息，之后才在 Python 中过滤目标群。复现：g1 先有 100 条，g2 再有 30 条，调用 g2、游标 0、limit 100，返回空列表和游标 0。由于 too_few 不推进游标，以后仍反复扫描 g1 的前 100 条，g2 有数据也学不到。

最小修改：把群过滤放到 SQL WHERE 中，参数化占位符，再 ORDER BY/LIMIT；维持每群游标现有语义。

### 3. P1：读取 100 条、模型只看 40 条，却推进到第 100 条

位置：`prompt.py:9–23`、`learning.py:141–177`。

默认 max_batch=100，但粗筛/提炼提示词 cap=40。复现中粗筛输入没有第 41 条，process_group 仍返回 advanced=true、max_id=100。调用方据此推进游标后，41–100 条从未被模型审查就被跳过。nothing_to_learn 分支也有同样风险。

最小修改：让读取批量与实际提交模型的批量一致，或只推进已处理区间的游标；不能仅靠“成功才推进”保证没有漏数据。

### 4. P1：当前预算门不是全局额度，后台学习缺少来源会被直接拦截

位置：`main.py:155–180`、`main.py:206–214`；现有 `dafeiyu_runtime/session_budget.py`。

对线上现有预算实现只读验证：ORIGIN 为空时，status 返回 `(False, '未确定来源会话，暂停辅助付费请求')`。新插件定时任务没有为当前 group_id 设置完整来源会话，因此配置 provider 后也不能正常通过后台预算检查。这里不是“某个群被全局预算先拦”，而是来源缺失。

此外，runtime 导入失败或 use_budget_gate=false 时 `_ask` 会直接调用模型，与 §17.11“所有调用必须走预算门”不一致。

最小修改：复用现有 scope，将归档 session_id 核对为完整、真实的来源会话，再包住两段调用；依赖缺失时禁学并提示，不应放行。不要猜测或伪造群来源，也不要改日常预算。

### 5. P1：真实框架会截掉多词命令参数，审批命令不可用

位置：`main.py:282`。

当前 AstrBot CommandFilter 在有参数默认值时采用默认值作为转换依据，`arg: GreedyStr = ''` 被当成普通字符串，而非贪婪字符串。用服务器实际 CommandFilter 验证：

```
['状态']            => {'arg': '状态'}
['通过', '1']       => {'arg': '通过'}
['黑话', '通过', '1'] => {'arg': '黑话'}
```

因此状态、列表能用，不代表审批能用；后者永远收不到编号。

最小修改：沿用已经验证过的无默认值 GreedyStr 写法，并用实际框架解析器验证无参、审批和黑话审批。

### 6. P2：数据库等待不在 hook 超时保护内，会阻塞回复事件循环

位置：`store.py:61`、`main.py:249–258`。

当前 Store 读写都是同步调用；to_thread 只执行纯函数 build_block，并不访问 SQLite。因此“后台任务与 hook 共用连接”本身不构成当前代码里的线程竞争，check_same_thread=False 也不是锁保护。

真正已复现的风险：独立连接持有写锁时，approved 同步等待锁。临时库持有 EXCLUSIVE 锁 1.5 秒，approved 实测阻塞约 1.53 秒；这段发生在 wait_for 之前。timeout=10 还允许等待约 10 秒，超过 §17.12 的 1.2 秒注入预算，并阻塞同一事件循环其他工作。

最小修改：在存储层给可选注入读取采用短锁等待、失败即跳过；或使用独立连接把完整读取移出事件循环，超时覆盖整个读取/拼装链路。单纯增加重试或把 timeout 再加长会加重问题；不能把现有共享连接直接分发到多个线程而不管理访问。

### 7. P2：配置热读取和关闭语义不完整

位置：`main.py:243–245`、`main.py:361–368`、`config.py:58`。

inject_style 不刷新配置，修改 enabled=false 后仍可能继续注入，直到命令或下一次 90 秒循环刷新。手动“跑一次”没有检查 enabled 和 groups，关闭学习或不在测试白名单的群仍能走学习入口。

另已复现：PowerShell 常见 UTF-8 BOM 配置会触发 JSON 解析失败，整份回落到默认值。原文件即使写 enabled=false，加载结果仍为 true，groups 回到空数组全群。这符合“失败回默认”的文字约定，但与关闭/测试范围的预期冲突，不能作为安全的关闭方式。

最小修改：接受 utf-8-sig，入口一致执行热读取、总开关和群范围检查；配置损坏时至少不能把已关闭/受限范围静默变成启用全群。不要提高预算或扩大群范围。

### 8. P2：非目标边界及 evidence 契约没有实现校验

位置：`learning.py:84–116`、`store.py:120–140`、`main.py:155–180`。

- 提示词要求每项有 evidence，但 parser 仅保留 rules 的 evidence，jargon/few_shots 的 evidence 被丢弃；规则 evidence 也不校验是否来自本批原文，甚至可为空。不能把“强制原文证据”写成已落实的数据保证。
- §17.4 不保存聊天原文；≤120 字证据是后文明确允许的例外。few_shots 却可以原样落库 user_text 200 字和 bot_reply 300 字，没有检查它是抽象示例还是原文复制；当前实现不能保证这一非目标。
- provider 仅按配置名称调用，没有保证“免费模型或 DeepSeek”；可以配置到其他付费模型。默认空 provider 并不产生费用，但“任何非 DeepSeek 付费调用都不会发生”没有被代码保证。这里只确认可绕过，未证明已实际发生收费。

最小修改：实现现有文档要求的来源证据校验、保存范围和模型费用限制；无需扩展到新平台或新增数据源。

## 二、10 个未验证点的逐项结论

| 项 | 结论 | 是否需要改 |
|---|---|---|
| 1 数据目录前缀 | 当前实际 StarTools 源码直接使用传入名字，不自动加前缀；`dafeiyu_style` 就是目录名。当前 memory.db 位于 `dafeiyu_daily_memory`，双目录回退可找到 | 当前定位可用；文档中的 style 配置路径需与实际目录一致 |
| 2 QQ 群号 | 当前 get_group_id 直接读 message_obj.group_id；openid 本身是正常标识，不能据此断言失效 | 需对照归档同一会话，暂未实测本插件真实 hook；列为待验收，不当成确认故障 |
| 3 容器时区 | 实测 TZ=Asia/Shanghai，当前本地时间为 +08:00 | **当前不会偏移**；若要求换环境也固定北京时间，改为显式 ZoneInfo，属修复可移植性 |
| 4 SQLite 并发 | 同事件循环里的同步读写不会因为协程而同时访问同一连接；外部锁导致同步阻塞则已复现 | **需要改超时覆盖和锁等待**，不是盲目加重试 |
| 5 截断 JSON | 不可解析即不推进游标，属于保守失败策略，不会保存半截 JSON | 不必做猜测式补全；需修正“截断修复已实现”的表述。类型错的合法 JSON 会变空对象并推进，和非法 JSON 不同 |
| 6 无 schema 面板 | 与手动配置设计相符，不影响核心运行 | 不需要加 WebUI 或 schema 新功能 |
| 7 全局预算 | **文字描述过时**，当前是来源会话预算；后台无来源被拦，另有绕过预算分支 | 必须按现有预算契约修复，见问题 4 |
| 8 私聊不生效 | 注入与“跑一次”确实跳过私聊；但列表 group_id='' 会调用 pending 的全群分支，管理员私聊可列出全群待审 | 需明确采用既定的群限定语义，或修正文档；“私聊列表不生效”与代码不符 |
| 9 已审批不可回滚 | review 只允许 pending → approved/rejected，确实实现且测试通过 | 属设计决定，不要求新增撤销功能；回滚可按已有关闭注入方案执行 |
| 10 首次配置时序 | 先加载默认值再写同样默认值，没有首轮行为差异 | 时序本身无需改；BOM/损坏配置回默认问题另见问题 7 |

## 三、其余接口契约对照

| 接口/约定 | 对照结论 |
|---|---|
| read_events 返回 (rows,max_id) | 签名、失败返回值一致；群过滤与批量游标语义存在问题 2、3 |
| parse_payload 数量 6/5/3 | 数量截断成立；字符串化把部分坏值变成 'None' 等有效内容，evidence 保证不成立 |
| process_group ask 参数与异常 | 两阶段 stage 名称一致；ask 异常向上抛。合法空 payload 会被算作成功，不能一概把语义无效输出视为“解析失败” |
| build_block 空/坏行 | 常规列表中的坏行会跳过，长度限制成立；若传非可迭代规则或非法 max_chars，仍会抛异常，接口“坏输入一律返回空”的表述过宽。生产 hook 会兜底异常 |
| review 白名单与状态机 | 表名白名单、pending 条件成立；状态修改与 review_log 分两次 commit，不能承诺原子审批日志 |
| SQL 只在 store.py | 不符，learning.py 直接含 memory.db 查询 SQL；只是架构约定偏差，不是 SQL 注入证据，查询值仍参数化 |
| 每日 1 次模型调用/群 | 实际一轮通常为粗筛、提炼 2 次；文档“两段式必须”与资源表“1 次”相互冲突，应修正文档口径，不要求删除阶段 |
| 日配额与总量 | enforce_caps 实际限制 pending 保留数，不是按日期累计新增数；只裁剪 style_rules，不裁剪黑话/示例。50MB 与总 60 条不能据此称为已保障 |
| 03:00 任务 | 当前时区正确，但 last_run_day 在学习前写入，失败后当天不会自动再跑；90 秒轮询是 03 点内触发，不是严格 03:00:00 |
| 原始数据源 | memory.db 使用 mode=ro，未发现写回该库；未发现修改 system_prompt、人格文件、主动发言、回复决策、PostgreSQL 或新增 pip 依赖 |
