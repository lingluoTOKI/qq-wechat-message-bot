# 上下文工具与长历史压缩验收

日期：2026-10-30。本轮完成只读配置/源码检查、历史事件取证、隔离 HTTP 请求序列化验证，以及一次性授权的真实模型合成对话验收。未改线上配置、未重载插件、未重启机器人或游戏服、未发送 QQ 测试消息。

## 结论与上线决策

1. 27 个工具可以解释为 **17 个白名单工具 − 1 个未启用的语义表情工具 + 11 个框架追加工具**。白名单约束人格工具装配，不会阻止框架随后追加内置工具。
2. 普通与主动回复没有共用最终工具装配流程。普通路径的隔离请求发出 27 个工具定义；主动插件直接构造 ProviderRequest，其初始 func_tool 为 None，经现有适配器和提供商序列化后没有工具定义。不能把这种 None 与“人格 tools=null 表示全部工具”混为一谈。
3. 默认摘要在本组样本的续问中为 8/9，候选规则为 9/9。默认摘要丢失一次具体提问，只留下泛化的兴趣标签。两者都保留了两个音乐任务的归属和编号。
4. **暂不下调线上压缩阈值，不设置 max_turns 硬截断。** 建议先统一请求装配与工具范围，再验证更多中文密集、工具往返和多次压缩样本。当前单样本不能证明降低阈值能节省费用或不损伤聊天质量。

当前 meme_manager 配置 `semantic.enabled=false`，`semantic.embedding_provider_id` 为空。插件在语义检索不可用分支移除 `search_memes`，所以人格工具实际剩 16 项；这不等于整个表情插件关闭。

检查依据：当前 `/AstrBot/astrbot/core/astr_main_agent.py` 的 `_ensure_persona_and_skills`、`_apply_kb`、`_apply_local_env_tools`、`_proactive_cron_job_tools` 和 build_main_agent；当前 meme_manager 的 `_remove_semantic_tool`。

### 普通与主动路径对照

| 路径 | 源码与隔离验证结果 | 证据边界 |
|---|---|---|
| 普通回复 | 人格工具 + 内置工具为 28 项，语义工具不可用后为 27 项；实际 OpenAI 提供商生成的 HTTP 请求含这 27 项，序列化会重新排序 | 使用当前框架装配函数、真实内置工具、惰性人格工具桩，HTTP 为 MockTransport；没有执行任何工具 |
| 主动回复 | llm_adapter._build_provider_request 不设置 func_tool；_invoke_provider 将 None 传入提供商，HTTP 请求不含工具定义 | 使用当前适配器方法与实际提供商序列化；插件钩子未整体运行，仅另行检查现有工具修改位置 |

这是历史记录、当前源码和隔离提供商边界的交叉核对，**不是在线进程两次真实请求的完整链路抓包**。现有 wire 快照主要保留哈希，无法事后恢复完整工具名；trace_enable 当前关闭。本轮没有为了取得更多证据而启用全文追踪或触发真实主动消息。

当前额外的 7 个本地运维工具在群聊里仍占定义体积，即使执行权限配置为普通成员不能执行。建议后续把运维能力限定到明确的管理员操作入口；群聊保留游戏、音乐、记忆、检索等必要工具。知识库工具与 query_project_info 的内部知识库检索也有重叠，需先明确各自范围再删除。不能只为了把数字变成 17 而删除需要的发送、历史查询或定时工具。

## 固定长对话与真实模型结果

样本由 50 轮合成群聊、1 条 system、1 条当前追问组成，共 102 条消息、27,278 字符。关键事实为中文，背景填充主要为英文；这是可控长对话，不是用户真实群聊，也不代表全部中文密集场景。

涵盖：人物归属、不同人物音乐偏好、饮品偏好更正、人物自建机器人与小洛的区别、向小洛提问这一兴趣线索、调试文本排除、暂定计划、跨用户同序号的原唱/翻唱任务，以及连续追问中的“它”。

使用线上配置指定的压缩模型 `xiaomi/mimo-v2.6-flash` 和当前实际 LLMSummaryCompressor。两组均保留最近 25% 的估算 Token，按完整轮次拆分；本次原样保留了最后 21 条非 system 消息。

为限制费用，本次真实 API 调用使用 `thinking=disabled`、`temperature=0`、`max_tokens=1400`、不重试。**并非完全复刻线上提供商全部参数。** 两次摘要由当前实际压缩器产生；两次续问也用 MiMo，以固定问题检查摘要可用性，没有调用主聊 DeepSeek 或实际续跑音乐任务。

结果经必要事实自动检查与逐项人工阅读；关键词检查只检测缺失，不替代语义审核。负例测试确认未知答案、跨用户交换音乐任务、虚构送达不能被计为通过。此处 9/9 是这一组样本的结果，不是通用正确率。

框架同一估算口径：原始 8,395 Token；默认压缩后 2,340；候选压缩后 2,375，候选约减少 71.7%。这些是估算，**不能当成用户那次 23,556 Token 请求的实测降幅，也不能据此计算实际节费比例**。

隔离安全检查还确认：压缩失败或返回空摘要时保留原始消息；system 和当前用户请求保持原对象。未额外验证调用方失败后的截断回退、完整工具调用往返、多轮反复压缩或真实音乐任务恢复。

## 本次一次性测试费用

用户授权上限 0.20 元，仅用于合成测试。实际 4 个成功 API 请求，无付费重试；返回输入共 15,913 Token，输出共 1,166 Token。按标准输入 1 元/百万 Token、输出 2 元/百万 Token，不计缓存优惠，估算 **0.018245 元**。最终结算仍以官方账单为准。

价格依据：[MiMo 官方价格页](https://mimo.mi.com/docs/pricing)。调用前以 UTF-8 字节上界、消息封装余量、输出上限和两倍价格余量预留；已完成请求按返回用量释放多余预留。最后两倍无缓存估算占用为 0.03649 元。中途保守预留曾拦住第四次调用，随后基于已返回用量续跑，未重复前三次请求。

独立验收进程将测试用量写入单独的 paid-records.json，没有写入机器人日常预算数据库；官方账号仍会正常计费。本轮未调整私聊不限额、每群每日 0.5 元的日常规则。

## 阈值与下一步实施范围

当前主聊天模型明确配置 64,000 Token 窗口，压缩器默认阈值 0.82，即框架计数高于 52,480 时满足压缩条件。`fallback_max_tokens=16000` 只在对应窗口无法确定时兜底，不能当成已经在 16,000 压缩。接口实际用量和框架估算计数口径不同，不保证精确在官方统计 52,480 时触发。

`max_turns=-1` 没有按轮数硬截断。源码说明轮数上限在压缩前执行；直接把它改成 40 或 50，可能先丢历史而非先生成摘要，因此本轮不这样改。

下一批实现建议：

1. 使用公共的请求策略统一普通和主动回复的人格、固定规则及必要工具，主动路径还要验证工具执行闭环，不能只传入工具定义。
2. 确认管理工具和群聊工具的具体范围后，一次性稳定列表；不要按每句关键词频繁增删定义。
3. 先灰度候选摘要规则，保留当前窗口、触发比例和 0.25 最近原文比例；增加中文密集、真实工具往返的合成样本和重复压缩测试后，再评估是否提前压缩。
4. 如未来降低阈值，需要比较压缩调用费用、缓存重新建立期间费用、后续未缓存输入、首字耗时，以及同一组连续对话的正确性。不得只比较压缩前后的消息数。
